# Database and Retrieval Design

## 1. MVP decision

Use **Qdrant** as the vector database for document chunks, embeddings, and searchable metadata. Keep original uploaded files in `python-ai/data/uploads/`. **A relational SQL database is not required for the core assignment.**

Recommended split:

- **Qdrant:** vectors, chunk text, and payload metadata used for retrieval and citations.
- **Original files:** `python-ai/data/uploads/`.
- **In-memory/application metadata:** track ingestion status while the service is running, or persist minimal document metadata as JSON only if needed for the assignment. Add SQL later only if user accounts, permissions, robust audit history, or more complex lifecycle management become requirements.

Qdrant deployment choices:

- **Local:** run Qdrant with Docker and set `QDRANT_URL=http://localhost:6333`.
- **Cloud:** create a free Qdrant Cloud cluster and set `QDRANT_URL` to its cluster URL and `QDRANT_API_KEY` to its key. Do not commit the API key.

## 2. Logical entities

### Document

| Field | Type | Purpose |
|---|---|---|
| `document_id` | UUID/string | Stable document identifier |
| `filename` | string | Original filename |
| `content_hash` | string | Detect duplicates or changed content |
| `mime_type` | string | Detected file type |
| `uploaded_at` | ISO timestamp | Ingestion time |
| `status` | enum | `processing`, `ready`, `failed` |
| `chunk_count` | integer | Number of indexed chunks |
| `error_message` | nullable string | Safe failure reason |

### Chunk / Qdrant point

Each chunk is stored as a Qdrant point.

| Field | Stored as | Purpose |
|---|---|---|
| `chunk_id` | Point ID | Stable chunk identifier |
| `embedding` | Vector | Numerical representation generated by the embedding model |
| `text` | Payload | Text used in retrieval and generation |
| `document_id` | Payload | Parent document identifier |
| `filename` | Payload | Source filename |
| `chunk_index` | Payload | Position in document |
| `page_number` | Payload, nullable | Page number when available |
| `section_title` | Payload, nullable | Heading/section when available |
| `start_char` / `end_char` | Payload, nullable | Text offsets when available |
| `content_hash` | Payload | Supports duplicate detection |

### Optional query log

Store only what is needed for debugging/evaluation: query ID, question (if permitted), retrieved chunk IDs, outcome (`answered`, `fallback`, `error`), and timestamp. Avoid logging secrets or sensitive document content. A SQL database is unnecessary for this optional MVP logging; use structured application logs unless persistent analytics are specifically required.

## 3. Qdrant collection

Collection name: `knowledge_chunks`.

Configure the collection vector size to match the selected embedding model's output dimension and use the distance metric appropriate for that model (Cosine is a common starting point). Do not hard-code a vector size until the embedding model is chosen.

Each point contains:

- ID: stable `chunk_id` (UUID is a convenient choice).
- Vector: embedding generated by the configured embedding model.
- Payload: `document_id`, `filename`, `chunk_index`, `text`, `page_number` when available, `section_title` when available, and `content_hash`.

Use deterministic or stable point IDs and upsert semantics to avoid duplicate chunks on repeated ingestion. Add payload indexes for fields such as `document_id` if filtering/deleting by document becomes important.

## 4. Ingestion transaction strategy

1. Validate file type and size.
2. Extract text and reject blank output.
3. Chunk while retaining source metadata.
4. Generate embeddings.
5. Upsert chunk points with their payload metadata into Qdrant.
6. Mark the document ready only after successful indexing.
7. On failure, mark it failed and clean up any partial points for that document.
8. On replacement/deletion, delete all points matching `document_id` and remove the stored source file if retained.

Qdrant writes and local file operations are not one shared transaction. Implement cleanup and status handling so a partial failure does not leave a document falsely marked as ready.

## 5. Retrieval

- Embed each question using the **same embedding model** used for document chunks.
- Search Qdrant for the top 4--5 nearest points by default.
- Preserve source metadata and the returned similarity/distance score.
- Filter/deduplicate results and apply a calibrated relevance threshold or evidence validation to trigger fallback.
- Similarity alone is not proof; answer generation must be constrained to actual retrieved text.
- If Qdrant is unavailable, return a controlled retrieval error; do not ask the LLM to answer without evidence.

## 6. Citations

A citation can show: `employee_handbook.pdf · Page 4 · Leave Policy`.

For `.txt`/`.md`, use filename and section or chunk index. Render only metadata actually stored; never fabricate a page or heading.

## 7. Configuration and privacy

- `QDRANT_URL=http://localhost:6333` for local Docker, or the URL of the Qdrant Cloud cluster.
- `QDRANT_API_KEY=` for local mode; set the secret value for Qdrant Cloud.
- `QDRANT_COLLECTION=knowledge_chunks`
- `UPLOAD_DIR=./data/uploads`
- `TOP_K=4`
- `CHUNK_SIZE=800`
- `CHUNK_OVERLAP=120`
- `SIMILARITY_THRESHOLD=` (calibrate for the chosen embedding model and score semantics)

Keep upload directories out of version control if documents may be private. Keep model and database credentials in the Python AI service environment only. Never expose `QDRANT_API_KEY` in frontend variables or return it from an API endpoint.
